# Corporate Policy: AI-Assisted Software Development Life Cycle (AI-SDLC) Control Policy

**Document ID:** POL-SEC-AISDLC-001  
**Version:** 1.0  
**Effective Date:** October 18, 2026  
**Review Cycle:** Annual  
**Owner:** Information Security & AI Systems Architecture  
**Applies To:** All engineering repositories, CI/CD pipelines, autonomous coding agents, and local worker runtimes  
**Regulatory Cross-References:** SOC 2 (CC6.8, CC8.1), NIST SP 800-53 Rev. 5 (AC-5, AC-6, CM-3, SA-11), NIST AI RMF 1.0 (GOVERN 1.2, MANAGE 2.4), ISO/IEC 42001:2023 (Clauses 6.1, 8.2, Annex A.6, A.9)

---

## 1. Purpose and Objective

This policy defines mandatory technical controls, verification standards, and cryptographic audit requirements for software developed using Artificial Intelligence (AI) models, Large Language Models (LLMs), or autonomous coding delegates.

The objective is to advance software engineering from manual, point-in-time procedural controls to continuous compliance by construction. All AI-generated code integrated into production systems must be verifiably safe, structurally tested against known defect models, resistant to hallucinated logic, compliant with separation-of-duties mandates, and traceable via non-repudiable audit logs.

---

## 2. Risk-Based Tiering Architecture

Software components are partitioned into three governance tiers. The tier dictates the required verification rigor and audit evidence:

| Governance Tier | Scope & Paths | Verification Standard | Audit Evidence Required |
| :--- | :--- | :--- | :--- |
| **Tier 1: Core Primitives** | Foundational algorithms, rate limiters, synchronization primitives, crypto routines (`tools/**`, `src/core/primitives/**`). | Automated discrimination testing against known defective mutants; independent local worker execution. | Cryptographically sealed dual-attestation entry in the delegation ledger (`refs/notes/delegations`). |
| **Tier 2: Protocol Engines** | State machines, event processors, serialization/deserialization logic sans direct I/O (`src/core/protocol/**`, `src/engine/**`). | In-memory loopback suites, golden-trace regression runs, invariant verification. | Automated CI verification pass and signed merge commit. |
| **Tier 3: Imperative Shell & UI** | API route handlers, UI/DOM components, CLI formatting, script glue (`src/routes/**`, `src/ui/**`, `scripts/**`). | Standard static analysis, AST import boundaries, cyclomatic complexity limits, unit/smoke suites. | Peer code review and clean Continuous Integration (CI) status. |

---

## 3. Approved AI Tooling & Data Boundaries (ISO 42001 Annex A.9)

1. **Authorized Local Runtimes:** Generation of Tier 1 core primitives must occur strictly within approved, sandboxed local inference environments (e.g., local execution nodes running authorized models such as `qwen/qwen3.8-27b`).
2. **Confidentiality & Zero Egress:** Proprietary business logic, authentication secrets, and sensitive system parameters must never be transmitted to external or commercial model training loops.
3. **Execution Sandboxing:** AI workers operate under least-privilege constraints without direct write access to protected branches or deployment keys.

---

## 4. Separation of Duties and Anti-Self-Approval (SOC 2 CC6.8, NIST AC-5)

1. **Role Independence:** Automated workers, models, or agents may generate candidate source code, but cannot approve, certify, or deploy their own output.
2. **Human Attestation:** Every Tier 1 software component generated by an automated delegate requires explicit review and attestation by an authorized human engineer.
3. **Cryptographic Identity Verification:** Approvals must be bound to a unique, non-repudiable reviewer identity using an authorized Ed25519 key pair. The attestation harness mechanically enforces anti-self-approval: if the worker's key fingerprint matches the reviewer's key fingerprint, the attestation engine halts and rejects the entry.

---

## 5. Verification & Discrimination Testing Standards (NIST AI RMF MANAGE 2.4)

1. **Pre-Implementation Contract Authoring:** Before an automated worker generates candidate code for a Tier 1 component, a formal verification contract defining functional boundaries and invariant conditions must exist.
2. **Defect Discrimination (Negative Fixture Verification):** All verification contracts must be validated against a known defective mutant fixture (`*.negative.ts`). The test harness must verify that the verification suite detects and rejects defective implementations before executing against candidate code.
3. **Flake Detection Loop:** Candidate code must pass a minimum of three (3) consecutive, deterministic verification cycles in clean sub-processes (`UNIT_PASSED`) without timing drift or state leaks.

---

## 6. Architectural Boundary Controls & Anti-Evasion (NIST SA-11)

1. **Inward Import Restrictions:** Core application logic and production engines are prohibited from importing un-attested utility logic from Tier 3 directories. Enforced via Abstract Syntax Tree (AST) architectural linting (`dependency-cruiser`).
2. **Complexity Ceilings on Glue Paths:** Tier 3 paths enforce static cyclomatic complexity ceilings (maximum complexity: 10; maximum function length: 40 lines). Complex algorithmic routines inlined into glue code to bypass Tier 1 governance will fail CI build gates automatically.
3. **Build-Time Graph Auditing:** The production deployment compiler resolves the complete dependency graph. If an algorithmic primitive missing a verified delegation record is detected, the build process terminates with a non-zero exit code.

---

## 7. Audit Evidence, Ledger Maintenance & Retention (SOC 2 CC8.1, NIST AU-6)

1. **Immutability of Delegation Records:** Audit records for Tier 1 components are stored within Git's object database under the dedicated ref `refs/notes/delegations`.
2. **Record Contents:** Each signed delegation record permanently records:
   - Target source file and commit tree SHA.
   - Authorized model identifier (e.g., `qwen/qwen3.8-27b`).
   - Hash of prompt and contract specification.
   - Worker cryptographic receipt.
   - Human reviewer identity and signature timestamp.
3. **Audit Verification Tooling:** Compliance verification is validated via `node scripts/verify-delegation-ledger.cjs`. A zero exit code across all ledger entries is mandatory for branch merge and production release.
4. **Retention Period:** All cryptographic delegation records and associated Git commit histories must be retained for a minimum of seven (7) years to satisfy regulatory audit requirements.

---

## 8. Enforcement & Exceptions

1. **Automated Enforcement:** Enforcement is automated via Git pre-commit hooks, CI/CD branch protection, and production compiler checks.
2. **Emergency Changes:** In the event of an urgent production incident (P1), an emergency patch may be deployed under the Standard Emergency Change Control Policy, provided a retrospective audit and signed delegation attestation is completed within twenty-four (24) business hours.
3. **Sanctions:** Willful evasion of architectural boundaries or deliberate tampering with audit notes is subject to formal disciplinary action.
